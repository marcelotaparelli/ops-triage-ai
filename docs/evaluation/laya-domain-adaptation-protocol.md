# Experiment B: Laya domain adaptation protocol (pre-training)

Experiment A remains an immutable zero-shot comparison. This separate experiment starts from the **same English base checkpoint** `convaiinnovations/laya` at revision `55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851`, not the externally specialised `laya-typed-decisions` checkpoint. Jev 1.13 remains the previously measured hosted zero-shot result; there is no Jev training run. Nothing in this protocol changes the HTTP runtime or `HybridPolicy`.

## Primary sources and training method

The [official v0.3.23 Kaggle two-T4 fine-tuning notebook](https://github.com/NandhaKishorM/laya/blob/v0.3.23/notebooks/laya_finetune_typed_decisions_2xT4_kaggle.ipynb), [official single-process MPS/CPU script](https://github.com/NandhaKishorM/laya/blob/v0.3.23/notebooks/laya_finetune_typed_decisions_mps.py), and [official fine-tuning guide](https://github.com/NandhaKishorM/laya/blob/main/docs/finetune.md) implement training directly with PyTorch and Laya's `build_model`, `build_sequence`, `render_options`, and `proper_reward`; there is no higher-level public `Agent.fit` used by those examples. The [repository](https://github.com/NandhaKishorM/laya), [release](https://github.com/NandhaKishorM/laya/releases/tag/v0.3.23), [base model card](https://huggingface.co/convaiinnovations/laya), and [typed-decisions card](https://huggingface.co/convaiinnovations/laya-typed-decisions) supply the version, model, licensing, and checkpoint context.

The official notebook tokenizes each `(state, question)` into one decision item with option markers. For `choice`, the target vector follows dictionary option order. It trains the encoder and decision head with AdamW, cosine learning-rate schedule, gradient clipping, gradient checkpointing, four reward samples with noise reduced across epochs, a proper-scoring-rule policy-gradient term, and cross-entropy to the target distribution. Its example uses 1,200 *cases* with five decisions per case, two 16-GB T4 GPUs, fp16 autocast, four epochs, microbatch eight per GPU, gradient accumulation four, encoder LR `2.5e-5`, head LR `1e-4`, and weight decay `.01`. It withholds a slice of the training dataset for temperature fitting. The CPU/MPS script uses a microbatch of two and accumulation 16 by default, but its CPU fallback is an API path, not a claim that a four-GB CPU host is practical for full fine-tuning. Both examples save `model.safetensors`, encoder/tokenizer files, and `rl_agent_config.json`. There is no guarantee of deterministic GPU kernels; seed, library versions, data hashes and hardware must accompany results.

Our dataset has **three decisions per ticket**, a smaller 512-token context and only 7/4/3 answer choices. The committed [training configuration](../../scripts/laya-adapt-training-config.json) sets one CUDA GPU with at least 14 GiB VRAM, fp16 autocast/fp32 master weights, four epochs, microbatch four decisions and accumulation eight (effective batch 32). It keeps the official encoder/head rates, AdamW, cosine schedule, reward samples and loss terms, but halves the notebook's per-GPU microbatch for a single 16-GB T4. It caps training at 3,600 seconds and records a USD 3 planning ceiling; a provider billing cap must still be set separately if cloud GPU is used. Keep the Experiment A question text and option order, so improvement is attributable to domain training rather than prompt changes. The base checkpoint's shipped temperatures are used for pre-training validation. Candidate fine-tuned checkpoints use temperature 1.0 and no inherited option-bucket overrides; no post-training temperature fit is planned, avoiding calibration fit and assessment on the same small validation split. Brier/ECE will therefore describe the uncalibrated candidates. The selected inference method must be frozen before held-out use.

Unlike the official demonstration's teacher-provided **soft** gold distributions, our independently authored tickets have deterministic class labels. Each training target is therefore a **one-hot distribution** in the original option order. The same reward and cross-entropy equations accept these targets, but this is a material difference from distilling a probabilistic teacher and may affect confidence calibration. We will report it explicitly rather than imply exact replication of the official benchmark recipe.

## Data construction and isolation

`scripts/laya_adapt_dataset.py` deterministically authors 1,120 TRAIN and 280 VALIDATION tickets from 33 hand-written scenario blueprints derived from the project's [operational taxonomy](../../src/infrastructure/ollama/ollama-prompt-v1.ts) and [priority/risk rules](../../src/application/classifiers/deterministic-triage-classifier.ts). It does not use an LLM, the frozen held-out file, or held-out errors. Scenario labels are assigned directly from their explicit operational facts; the generator never infers labels from a model response. Each split has distinct title/detail/context wording, varied operational surfaces, short and long tickets, ordinary and severe incidents, blocking regressions, access and security cases, and routine low-priority requests. Nine added blueprints deliberately include cross-category words (login guidance, incident dashboard ideas, editorial access-page copy, false permission previews, past incident notes, and test-only outages) to reduce superficial lexical shortcuts. Unrelated background context tests resistance to incidental vocabulary. The split is intentionally nonuniform and validation still shares underlying scenario families, so validation is not an independent real-world population. The script checks cross-split exact text uniqueness, and `--check` verifies byte-for-byte regeneration. The dataset artifact records category, priority, risk, joint-label and text-length distributions with SHA-256 hashes.

An initial pre-training tokenizer check on dataset v1 generated all 3,360 choice items through the official `build_sequence` path: zero dropped state tokens, zero collapsed options, and 117–226 tokens per item. The final v2 check also processed all 3,360 decisions without dropped state tokens or collapsed options; sequence lengths were 117–231 tokens. The original ticket and scenario ID do not enter the model state beyond title and description; labels become one-hot targets in the frozen option order.

Before any training or Experiment B held-out call, dataset v1 was revised to v2 following a structural review: v1 lacked enough explicit cross-category lexical distractors. A 280-ticket v1 base-validation **pilot** completed (280 valid, exact tuple 0.1143, 2/133 LOW priorities correct), but it began before the evaluation CLI was committed and is not the canonical validation baseline. A repeat against v1 was interrupted after 175/280 to avoid spending more CPU time on the superseded dataset. The pilot is retained locally outside tracked artifacts; it is not used to select a checkpoint or claim improvement. The v2 revision was made for scenario coverage, not in response to per-ticket held-out errors, and the held-out file was not read for dataset construction. A new complete base validation on v2 is required before training.

The 1,120/280 size gives roughly 3,360 training and 840 validation decisions. That is smaller than the official notebook's 6,000 training decisions but is a reasonable first domain experiment under a low GPU-cost objective. Validation is large enough for a modest checkpoint comparison, though rare category/severity cells remain small. No TRAIN or VALIDATION row comes from the 70-ticket held-out. The held-out stays at `datasets/triage-eval.jsonl`, 70 IDs, SHA-256 `e3864aaefba8327dff78a0e7680df55650c995664e29daea31aaab85abe63ab0`; it must not be read by training, checkpoint selection, calibration, threshold selection, or hyperparameter tuning.

## Planned evaluation and freeze

Evaluate the pinned base checkpoint on VALIDATION before training. Train on TRAIN only. Assess candidate checkpoints and any temperature fit on VALIDATION, recording per-field accuracy, category macro-F1, severe-class recall, exact tuple, Brier, ECE, confidence and coverage using the Experiment A definitions. Training loss is diagnostic and cannot replace validation. Optionally score TRAIN with the selected checkpoint to expose a generalization gap. A selection rule, inference settings, dataset/checkpoint hashes, code commit, hardware, precision and thresholds must be committed in a **Freeze 2** manifest before any new held-out inference. Then make exactly one official 70-ticket run with a distinct append-only attempt journal and result artifact. On operational failure, document before any rerun. Do not adjust the model or inference based on held-out errors.

The present host reports four virtual AMD EPYC CPUs, about 4 GB RAM, and no exposed GPU. A 421M-parameter full-parameter AdamW fine-tune has model weights, gradients, optimizer states and activations; it is not appropriate to launch a long CPU run here. A reproducible GPU option is the official notebook's two T4 path or a single GPU with sufficient VRAM and smaller microbatch. [Modal's published T4 rate](https://modal.com/pricing) is USD 0.000164/s per T4, plus CPU and RAM; its platform requires an account and payment method. This is a planning price, **not observed spend**. Actual provider, region, runtime and billed amount must be recorded if training is executed. Local inference has USD 0 external model-usage charge, with machine/energy cost unmonetized unless measured.

The final report must separate out-of-the-box deterministic/Ollama/Jev/Laya-base from adapted Laya, retain historical missing cells, and state that Jev saw no domain examples while tuned Laya did. It must investigate the base `40/40 LOW → MEDIUM` pattern without using it for checkpoint selection after seeing the frozen held-out.
